# 代码审查提示词

审查目标代码（默认审查 `git diff --cached` 的暂存改动；也可按需指定文件/路径/某个插件或模块范围）：
```
<target>
git diff --cached   （或指定文件清单/目录）
</target>
```
只读审查，不得修改任何文件。

## ⚠️ 语言硬性要求（最重要，先读这个）

想象你的读者是被拉来开会、没看过代码的**老板**。**先讲人话，再给技术细节**。具体规则：

1. **每条问题先甩一句大白话结论**，讲清楚三件事：**发生了什么 / 会不会出事 / 需不需要改**。技术细节（函数名、行号、报错名）放这句话**后面**当佐证，别一上来就堆术语。
   - ❌ 不说："writeJsonAtomic 的 mkdirSync 未被 try 包裹，破坏返回 false 契约，导致 unhandled rejection。"
   - ✅ 要说："**写文件时如果创建文件夹失败，程序会直接崩，而不是温和地告诉你失败了**——可能造成假死或无声报错。位置在 atomic-write.ts 里创建文件夹那句没包保护。"
2. **能说人话的词就说人话**："抛异常"可以说"崩溃/报错"，"竞态"可以说"两个地方同时动手打架"，"契约不符"可以说"说好的没做到"，"静默失败"可以说"出问题了也不吭声"。
3. **每条之后用一句话给"要不要管"的结论**：`不改会怎样` / `改一下要多久` / `不改也行`。
4. 别用"维度""契约""链路""单飞""tois斜面"这类词来**解释**，术语只能出现在技术佐证里，且出现一次后要跟人话翻译。

## 检查清单（内部对照用，不必逐条汇报）

1. **会不会崩/出乱子**：错误处理有没有漏洞、失败有没有兜底、网络失败会不会无声中断、并发会不会打架、空值/超大输入/边界会不会翻车
2. **说好的做到没**：跟外部接口字段/流程对不对得上、函数声明的"返回值/行为"和实际是否一致、功能齐不齐、有没有写了用不上的死代码
3. **安全**：路径穿越、注入、key/token 有没有泄漏到日志或文件、危险删除有没有二次确认
4. **慢不慢**：有没有重复请求/每次先查再写、上下文被撑大、算法复杂度
5. **好不好维护**：重复代码、改了一处漏了别处、注释和实际矛盾、有没有更省事的写法

## 分级（人话版）

- 🔴 **必改**：不改会导致**功能错、出安全问题、或者出问题了还不知道**（最坑，必须修）
- 🟠 **该改**：逻辑有毛病或明显绕远路，最好修
- 🟡 **可改**：边界/防御/代码美观问题，改不改都行
- 🔵 **建议**：加测试、补注释、顺手优化

## 输出格式

1. 开头先来一段**"三句话总览"**（最末一段也要有结论）：
   - 第一句：这堆改动**干什么用的、整体靠不靠谱**。
   - 第二句：**有没有必须动的地方**（没有就说"没有必须改的，可以放心合入"；有就列是哪几条）。
   - 第三句：**如果要改，先动哪个、为什么**。

2. 然后按 🔴→🟠→🟡→🔵 列出问题。每条格式：
```
【严重级】一句话大白话（发生了什么/会不会出事/要不要改）
  位置：文件:行号 / 函数名
  技术说明与建议：...（这里才允许放函数名、报错等细节）
```
> 正文中间不要跳过任何你实际发现的问题；某级没有就说"无"。

3. 末尾给一段**大白话总结**：`能合入吗 / 值得保留还是重写 / 先改哪个、为什么`，全程用人话，能一句话讲清的别绕三句。

> 说明：本提示词既用于暂存改动的快速审查，也用于对某个插件/模块做深度审查；先定清 target 边界，范围越大结论越含糊。
